# Phase 3: Code Review Report

**Reviewed:** 2026-04-12T00:00:00Z
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

The test infrastructure is well-structured with good coverage of security features (CSRF, rate limiting, timing-safe comparison, input validation, model routing). The mock helpers are clean and composable. However, the production source file (`src/index.ts`) has two XSS vulnerabilities in HTML template functions, and the test suite has a vacuous test that provides false confidence. The codebase also has significant duplication in tool handler error-handling blocks.

## Critical Issues

### CR-01: XSS in errorPage via unsanitized HTML interpolation

**File:** `src/index.ts:676-677`
**Issue:** The `errorPage` function interpolates `heading` and `message` directly into HTML using template literals without escaping. While currently only called with hardcoded strings (line 575-576), this is a stored XSS vulnerability waiting to happen. If any future caller passes user-controlled data, it becomes exploitable.
**Fix:**
```typescript
function escapeHtml(s: string): string {
  return s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;").replace(/"/g, "&quot;").replace(/'/g, "&#39;");
}

function errorPage(heading: string, message: string): string {
  return `...
    <h1>${escapeHtml(heading)}</h1>
    <p>${escapeHtml(message)}</p>
  ...`;
}
```

### CR-02: XSS in loginPage via unsanitized CSRF token in HTML attribute

**File:** `src/index.ts:706`
**Issue:** The `loginPage` function interpolates `csrfToken` directly into an HTML attribute value: `value="${csrfToken}"`. The CSRF token is generated by `crypto.randomUUID()` (line 566), which produces only hex and hyphens, so this is not currently exploitable. However, there is no defense-in-depth; if the token generation changes, this becomes an attribute-injection XSS. The function should escape the value regardless.
**Fix:**
```typescript
function loginPage(csrfToken: string): string {
  const safeToken = escapeHtml(csrfToken);
  return `...
      <input type="hidden" name="csrf" value="${safeToken}">
  ...`;
}
```

## Warnings

### WR-01: test:coverage script does not reference vitest.coverage.config.mts

**File:** `package.json:10`
**Issue:** The `test:coverage` script runs `vitest run --coverage` without specifying which config file to use. The `vitest.coverage.config.mts` file exists specifically for coverage (with node pool instead of cloudflare pool), but is never referenced. Vitest will default to `vitest.config.mts`, which uses the cloudflare pool -- the exact configuration the coverage config was created to avoid (per its own doc comment: "Istanbul instrumentation causes workerd to crash on startup").
**Fix:**
```json
"test:coverage": "vitest run --coverage --config vitest.coverage.config.mts"
```

### WR-02: Vacuous test in error-sanitization -- tests a constant, not behavior

**File:** `src/__tests__/error-sanitization.test.ts:41-49`
**Issue:** The test "auth 403 response says 'Invalid secret.' without revealing actual secret" does not invoke the auth handler at all. It constructs a local string `"Invalid secret."` and asserts it does not contain `"test-secret-pin"`. This will always pass regardless of what the auth handler actually returns, providing false confidence. The comment says "Integration test for this is in auth-flow.test.ts" but this test still gives a misleading green checkmark.
**Fix:** Either remove this test (it is redundant with `auth-flow.test.ts` line 190-193 which properly tests the handler) or rewrite it to actually invoke `authHandler.fetch` with a wrong PIN and assert on the response body.

### WR-03: Tests access private SDK internals via `(server as any)._registeredTools`

**File:** `src/__tests__/tool-handlers.test.ts:9`, `src/__tests__/input-validation.test.ts:8`
**Issue:** Both `getToolHandler` and `getToolSchema` cast the MCP server to `any` and access `_registeredTools`, an undocumented internal property of `McpServer`. This couples tests to the SDK's internal implementation. If `@modelcontextprotocol/sdk` changes its internal structure in a minor/patch release, all these tests break silently with confusing errors (the `throw new Error` on line 9/10 would fire, not a proper assertion failure).
**Fix:** This is a pragmatic choice given the MCP SDK's API surface, but it should be acknowledged with a comment and ideally isolated to a single helper function (which it already is). Add a comment noting the fragility:
```typescript
// WARNING: Accesses SDK internals. If this breaks after an SDK update,
// check McpServer's internal structure for the new property name.
function getToolHandler(env: Env, toolName: string) {
  ...
}
```

## Info

### IN-01: Significant code duplication in tool handler error blocks

**File:** `src/index.ts:206-215, 241-250, 271-280, 305-314, 328-336, 365-372, 400-408, 428-437, 452-468, 495-501, 525-532`
**Issue:** Every tool handler has an identical try/catch block pattern: check `err.message === "AI_TIMEOUT"`, console.error, return `makeToolError`. This is repeated 11 times. Extracting a wrapper function would reduce ~110 lines to ~11.
**Fix:**
```typescript
async function withAIErrorHandling(
  toolName: string,
  fn: () => Promise<string>,
): Promise<{ content: { type: "text"; text: string }[]; isError?: true }> {
  try {
    const text = await fn();
    return { content: [{ type: "text", text }] };
  } catch (err) {
    const msg = err instanceof Error ? err.message : "";
    const code = msg === "AI_TIMEOUT" ? "AI_TIMEOUT" : "AI_ERROR";
    console.error(`Tool error [${toolName}]: ${code}`);
    return makeToolError(code, toolName);
  }
}
```

### IN-02: Dual coverage providers in devDependencies

**File:** `package.json:22-23`
**Issue:** Both `@vitest/coverage-istanbul` and `@vitest/coverage-v8` are listed as devDependencies. Only Istanbul is configured in both vitest config files. The v8 provider appears unused and adds unnecessary install weight.
**Fix:** Remove `@vitest/coverage-v8` from devDependencies if Istanbul is the chosen provider.

### IN-03: wrangler.toml contains placeholder KV namespace ID

**File:** `wrangler.toml:13`
**Issue:** The KV namespace ID is `REPLACE_WITH_YOUR_KV_NAMESPACE_ID`. This is fine for a template/dev setup but will cause `wrangler deploy` to fail. If this is intentional (setup instructions), consider adding a comment. If it was meant to be filled in, it needs the actual ID.
**Fix:** This is likely intentional for the repo template. No action required unless deploy is expected to work from this config.
