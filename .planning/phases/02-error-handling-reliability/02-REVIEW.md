# Phase 2: Code Review Report

**Reviewed:** 2026-04-12
**Depth:** standard
**Files Reviewed:** 1
**Status:** issues_found

## Summary

Reviewed `src/index.ts`, the single-file MCP server containing all tools, auth handler, and model routing logic. The code is well-structured with consistent error handling across tools, proper timeout management for AI calls, and a self-healing model config mechanism. However, there are two critical XSS vulnerabilities in the HTML template functions, a type safety concern in the AI response handling, and significant boilerplate duplication across tool handlers that increases maintenance risk.

## Critical Issues

### CR-01: Reflected XSS in errorPage function

**File:** `src/index.ts:676-678`
**Issue:** The `errorPage` function interpolates `heading` and `message` parameters directly into HTML via template literals without escaping. While current callers pass static strings, the function signature accepts arbitrary strings. If any future caller passes user-controlled data (e.g., an error message derived from request input), this becomes a reflected XSS vulnerability.
**Fix:**
```typescript
function escapeHtml(str: string): string {
  return str
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#x27;");
}

// Then in errorPage:
//   <h1>${escapeHtml(heading)}</h1>
//   <p>${escapeHtml(message)}</p>
```

### CR-02: Reflected XSS in loginPage via csrfToken

**File:** `src/index.ts:706`
**Issue:** The `csrfToken` parameter is interpolated directly into the HTML `value` attribute: `value="${csrfToken}"`. The token is generated by `crypto.randomUUID()` which produces safe output, but the function itself does not enforce this contract. If the token source ever changes or is tampered with before reaching this function, an attacker could inject arbitrary HTML/JS. Defense-in-depth requires escaping output regardless of input source.
**Fix:**
```typescript
// In loginPage, escape the token:
<input type="hidden" name="csrf" value="${escapeHtml(csrfToken)}">
```

## Warnings

### WR-01: Unsafe type assertion on AI response

**File:** `src/index.ts:149`
**Issue:** The AI response is cast with `as { response?: string }` without runtime validation. If the Workers AI SDK changes its response shape (e.g., returns an array for streaming, or wraps in a different structure), this will silently produce `undefined` and fall through to `JSON.stringify(response)`, which may expose internal response structure to MCP clients. The fallback `JSON.stringify` path is also untested -- if `response` is a ReadableStream or contains circular references, this will throw.
**Fix:**
```typescript
// Add runtime validation:
if (typeof response === "object" && response !== null && "response" in response) {
  const text = (response as { response: unknown }).response;
  if (typeof text === "string") return text;
}
// Fallback with safety:
try {
  return JSON.stringify(response);
} catch {
  throw new Error("AI_ERROR");
}
```

### WR-02: CSRF token used as KV key without format validation

**File:** `src/index.ts:603`
**Issue:** The CSRF token from form data is used directly in a KV key lookup (`csrf:${csrfToken}`) after only checking it is a non-empty string under 256 characters. While KV keys are not vulnerable to injection in the traditional sense, an attacker could craft a token value like `../../config:model:fast` or any other KV key prefix to probe for the existence of other keys (the response differs between "not found" and "found"). Validating UUID format prevents key namespace confusion.
**Fix:**
```typescript
const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
if (!UUID_RE.test(csrfToken)) {
  return new Response("Invalid form data.", { status: 400 });
}
```

## Info

### IN-01: Duplicated try/catch boilerplate across all tool handlers

**File:** `src/index.ts:196-533`
**Issue:** Every tool handler (11 of 12) contains an identical try/catch block that checks for `AI_TIMEOUT` and falls back to `AI_ERROR`. This is ~10 lines duplicated 11 times (110 lines). If the error handling strategy changes (e.g., adding retry logic in Phase 2), every handler must be updated individually, increasing the risk of inconsistency.
**Fix:** Extract a wrapper function:
```typescript
async function withToolErrorHandling<T>(
  toolName: string,
  fn: () => Promise<T>,
): Promise<T | ReturnType<typeof makeToolError>> {
  try {
    return await fn();
  } catch (err) {
    const msg = err instanceof Error ? err.message : "";
    if (msg === "AI_TIMEOUT") {
      console.error(`Tool error [${toolName}]: AI_TIMEOUT`);
      return makeToolError("AI_TIMEOUT", toolName);
    }
    console.error(`Tool error [${toolName}]:`, msg || "unknown");
    return makeToolError("AI_ERROR", toolName);
  }
}
```

### IN-02: OAuth helpers extracted via unsafe cast

**File:** `src/index.ts:560`
**Issue:** `(ctx as unknown as { oauth: OAuthHelpers }).oauth` uses a double cast through `unknown` to extract OAuth helpers from the execution context. This bypasses all type checking and will silently produce `undefined` if the OAuthProvider wrapper changes how it injects helpers, leading to a runtime crash on the next line (`oauthHelpers.parseAuthRequest`). Consider adding a runtime guard.
**Fix:**
```typescript
const oauthHelpers = (ctx as unknown as { oauth?: OAuthHelpers }).oauth;
if (!oauthHelpers) {
  return new Response("Internal server error", { status: 500 });
}
```
