<objective>
Wire the Phase 6 `executeBatch` engine and Phase 5 `runTask` executor into a single new
`code_assist_batch` MCP tool — the repo's first structured-output tool. It declares Zod input and
output schemas, returns an order-preserving partial-results contract as `structuredContent`
alongside a human-readable `content` text summary, and sets MCP tool annotations. A new test file
proves the enriched output parses against the declared output schema for both all-ok and mixed
batches.

Purpose: Deliver the result contract (BATCH-07/08) and the tool registration (BATCH-09) that turn
the pure batch engine into a callable, schema-validated MCP tool behind the existing OAuth gate.
Output: Edits to `src/index.ts` (schemas + `deriveErrorType` + `runBatch` enrichment + registration
+ export-block additions) and a new `src/__tests__/batch-tool.test.ts`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client → code_assist_batch | Untrusted `tasks[]` array (kind + open-record input) crosses into the server |
| code_assist_batch → runTask → Workers AI | Per-task `input` is string-interpolated into Qwen prompts |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-7-01 | Tampering | Open-record per-task `input` (`z.record(z.string(), z.unknown())`) | mitigate | The open boundary defers validation, it does not skip it: each task's input is validated per-kind INSIDE `runTask` (`TASK_SPECS[kind].validate?`, e.g. transformCode's 8KB cap throwing ValidationError). A malformed task is isolated as a `status:'error'` entry (error_type derived by `deriveErrorType`) by executeBatch's per-task try/catch — it never rejects or poisons the sibling tasks. Asserted by the `mixed` test case (one bad task → others still status:'ok'). |
| T-7-02 | Spoofing / Elevation | New tool entrypoint | mitigate | `code_assist_batch` is registered on the SAME `McpServer` returned by `createMcpServer` (before `return server`, line 692) and therefore sits behind the identical `OAuthProvider` gate as all other tools — no new unauthenticated entrypoint is introduced. Asserted by the `registration` test (tool present in createMcpServer) and the unchanged OAuthProvider wiring. |
| T-7-03 | Denial of Service | Batch fan-out amplifier (N tasks × Qwen cost) | mitigate | Bounded by the `tasks` inputSchema `.max(50)` AND the pre-dispatch `BATCH_MAX_TASKS` cap (default 50) + `BATCH_CONCURRENCY` cap (default 6) + per-task `BATCH_TASK_TIMEOUT_MS` (default 45000ms) — all already enforced inside the Phase 6 `executeBatch`/`withTimeout`. No new unbounded loop is introduced by Phase 7; runBatch is a thin map over the already-capped result array. |
| T-7-04 | Tampering | `structuredContent` output integrity | mitigate | The SDK validates `structuredContent` against `BatchOutputSchema` on every non-error response (cannot be bypassed except via the explicit `isError:true` escape used only on the over-cap/unexpected-throw catch path). Asserted by the all-ok and mixed parse tests. |
| T-7-SC | Tampering | npm installs | mitigate | Phase 7 installs zero new packages (RESEARCH.md Package Legitimacy Audit: all deps pre-installed). No install task exists; no legitimacy checkpoint required. |

No `high`-severity threat remains unmitigated.
